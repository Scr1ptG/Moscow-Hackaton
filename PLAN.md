## 5. Список доп. фич для формы
- Map matching NDTP-треков на маршрут: детектор прибытий на остановки по GPS, калиброван по фактам АСДУ (медиана ошибки ~4 с).
- Ансамбль: LightGBM + CatBoost по табличным признакам + PyTorch GRU по последовательности телеметрии.
- Объяснимость: TreeSHAP-вклады → группы причин + правила-паттерны перед сбоем.
- Интервал прогноза (q10–q90) и вероятность опоздания.
- What-if анализ через переопределение признаков.
- ONNX-инференс и замеры latency.
- Деградация без падения: GPS/связь пропали → прогноз по последнему состоянию и плану; ML недоступен → эвристика.
- Реплеер исторических данных в NDTP для воспроизводимого демо.

## 6. Риски и находки, о которых должна знать вся команда
1. **Утечка ответа validate.** `train/schedule.csv` и `test/schedule.csv` содержат факт прибытия для **всех 151** целевых остановок validate, а `target = факт − план` в 100% разметки. Любая команда может получить скор 1.0 без модели. Мы это **не используем**: это прямо нарушает правило честности README. Рекомендую сообщить организаторам.
2. **`manual_fill` в `validate/schedule_plan.csv`** говорит, как будет записан будущий факт (0 или копия прошлой задержки). На момент T это неизвестно, в модели не используем.
3. **Синтетические ТС** в train — сдвинутые копии реальных ТС на весь день (задержки плюс шум σ≈20 с), включая периоды test/validate. Поэтому честная валидация только leave-one-vehicle-out. Оценка train→test оптимистична.
4. `MAE_TARGET` в формуле скора неизвестен. По test он оценивается в ~0.76·mae_zero (≈78 с), но на validate может отличаться.
